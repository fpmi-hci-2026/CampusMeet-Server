# CampusMeet REST API — контракт ЛР4

Единственный редактируемый источник маршрутов и схем — [scripts/export_contracts.py](../scripts/export_contracts.py). Он экспортирует [OpenAPI 3.0.3](openapi.json), [матрицу маршрутов](route-matrix.md), [Postman collection](CampusMeet.postman_collection.json) и [Bruno collection](bruno/). После изменения контракта запустите экспорт и тесты. Копия в портале документации обновляется отдельной командой из CampusMeet.

## Запуск и импорт

```bash
python3 scripts/export_contracts.py
python3 scripts/build_sqlite_schema.py
python3 -m campusmeet.mock_api
```

Базовый URL: `http://127.0.0.1:8000/api/v1`; спецификация: `http://127.0.0.1:8000/openapi.json`. Каталог Bruno открывается как готовая коллекция, окружение — `Local`. Для Postman импортируйте `CampusMeet.postman_collection.json`; OpenAPI можно открыть в Swagger Editor / Swagger UI. Аккаунт облачного сервиса для локального запуска не требуется.

Сгенерированные запросы показывают контракт каждой операции и работают независимо от порядка, кроме запросов к билетам: `tkt-example-01` и `DEMO-EXAMPLE` — **заполнители**, замените их ID и кодом из реальной регистрации. Для полного сценария используйте `scripts/smoke_http.py` на новой временной базе. Методы изменения примеров помечены `X-Mock-Mode: example` и не сохраняют данные.

## Соглашения

- JSON, UTF-8; даты ISO 8601 с часовым поясом; номера страниц начинаются с 1, `limit=1..100`.
- В базе сохранены строковые ID старой схемы. Параметры пути ограничены `A-Z a-z 0-9 _ -`, максимум 36 символов.
- Права: public, authenticated, owner, staff, organizer, captain. В stateful-маршрутах проверяются собственник билета, владелец мероприятия и назначение волонтера. В example-маршрутах моделируется контракт и базовая ролевая проверка; полной бизнес-авторизации еще нет.
- Демо-аутентификация принимает известный fixture user и возвращает `demo-*`. Это **не JWT и не настоящая проверка пароля**. Целевой сервер ЛР5–6 должен заменить ее на JWT с проверкой подписи и срока.
- `POST registrations`: обязательный `Idempotency-Key`, область ключа — пользователь + событие + операция. Повтор возвращает первоначальный ответ, новое тело с тем же ключом → 409. TTL/очистка ключей в MVP не реализованы.
- `PUT events/{id}`: полное редактируемое представление и обязательный `If-Match: "1"`; устаревшая версия → 412, отсутствие заголовка → 428. Для чтения/изменения события сервер возвращает `ETag`.
- Поле `status` входит в EventInput: организатор может сохранить черновик или открыть/закрыть регистрацию через POST/PUT; допустимые состояния перечислены в контракте.
- `Ticket.qr_payload` в mock содержит только синтетический DEMO-код для registered/checked_in и null для очереди/отмены. В целевом API это поле должно содержать подписанный payload; зарезервированы qr_token_hash/signature_key_id без хранения приватного ключа в билете.
- `DELETE ticket`: логическая отмена, без удаления аудита; повтор → 204. Использованный билет → 409.
- Чекин: `client_scan_id` уникален; повтор того же скана возвращает тот же результат, другой скан использованного билета → 409. Успешный проход уникален по ticket_id. В mock проверяется только синтетический `DEMO-*` код, криптографическая подпись не реализована.
- Ошибки: `application/problem+json`, поля `type,title,status,detail,instance,code`; общие коды документированы в OpenAPI. `429` предусмотрен целевым контрактом, rate limiting в mock не реализован.
- CORS `*` разрешен только для локальной демонстрации без cookie. Публикуемый производственный API должен ограничить источники.

## Пример регистрации

```bash
curl -i http://127.0.0.1:8000/api/v1/events
curl -i -X POST http://127.0.0.1:8000/api/v1/events/ev-campusmeet-2026/registrations \
  -H 'Authorization: Bearer demo-artem' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: registration-artem-001' \
  -d '{"join_waitlist":true}'
```

201 означает созданный билет со `status=registered` или заявку `status=waitlisted`; точный статус нужно прочитать в теле. При выключенной очереди или `join_waitlist=false` исчерпанная квота дает 409. Результат не доказывает доставку push или сохранение билета в мобильном SecureStore.

## Внешние интеграции и изменения относительно ЛР1–3

Целевые шлюзы Nominatim и Nager.Date вызываются сервером с таймаутом, кешем и обработкой недоступности, не блокируют сохранение черновика. В ЛР4 возвращаются фиксированные примеры. Проверка праздника — рекомендация организатору, не доказательство наличия аудитории.

Старые команды `/events/{id}/register`, `/tickets/validate-qr`, `/announcements/broadcast` заменены ресурсами `registrations`, `check-ins`, `announcements`. В ЛР1 они были предварительными и не имели реализации, поэтому backward-compatible alias не нужен. Адреса клиентов пока не реализовывались; новые маршруты заданы единственным контрактом.

HMAC требует **секретного ключа**, а не открытой соли. Для независимой офлайн-проверки целевая архитектура должна использовать подпись Ed25519 с открытым ключом на сканере; сам mock этого не реализует. Между двумя отключенными сканерами дубликат обнаруживается только при синхронизации. Apple Wallet / Google Wallet требуют ключей провайдеров; маршрут честно возвращает 501. Экспорт XLSX, push, офлайн-пакеты, CFP, команды и расписание пока являются контрактными примерами.
